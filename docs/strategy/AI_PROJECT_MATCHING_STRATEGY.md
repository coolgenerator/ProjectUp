# 基于 AI 的项目匹配：方向梳理与落地策略

> 状态：讨论稿（2026-10-30）
> 范围：ProjectUp 是否、以及如何转向"基于 LLM 的人 ↔ 项目匹配"。本文汇总了现状盘点、痛点分析、需求判断、中美市场对比、场景 brainstorm 与筛选结论。
> 相关文档：[INNOVATION_DANCE_COLLABORATION_ANALYSIS.md](./INNOVATION_DANCE_COLLABORATION_ANALYSIS.md)（与 Innovation Dance 的合作评估；若合作成立，会调整本文 §10 的功能取舍）

---

## 0. 一句话定位

**对用户：**
> 找队友全靠运气，组了队还有人摸鱼。ProjectUp 用 AI 把你的项目拆成具体角色，只推荐有证据、肯投入的人，先试用再组队。

**对投资人或评委：**
> 学生项目组队失败，根本原因不是找不到人，而是找不到靠谱的人。我们把"声称感兴趣"变成"可验证的投入"，用试用期和站内贡献记录建立信誉，让 AI 匹配的是可靠度，而不只是技能标签。

讲的时候注意两点：
- 痛点要落在"**靠谱**"上，不要落在"**找到**"上。找人这件事，微信群和小红书已经能做到。
- **AI 是手段，不是卖点。**用户要的是靠谱的队友，并不在乎背后是不是 LLM。

## 1. 现状盘点

### 1.1 代码规模与功能分布

| 部分 | 规模 | 主要内容 |
|---|---|---|
| backend（Go） | 约 4.6 万行 | 认证、项目、任务、工作区、聊天、论文、课程、订阅等约 30 组路由 |
| ai-service（Python） | 约 7.8 万行 | IdeaTree 节点对话、课程生成、论文分析、路线图、AI 引导建项目、RAG，另有 5 套并存的 workflow 引擎 |
| crawler（Python） | 约 1.9 万行 | 爬 GitHub awesome 列表，生成"领域/主题/概念"知识分类 |
| frontend（React） | 约 70 个页面 | 仅 IdeaForest 一块就有约 3.4 万行 |

现有文档里同时存在三种定位，彼此打架：
- `COMPETITIVE_ANALYSIS.md` 想做"面向知识工作的 AI 项目管理"；
- `IMMEDIATE_IMPLEMENTATION_PRIORITIES.md` 想补齐 Jira 那一套（任务依赖、自动化、工时统计）；
- `docs/IDEA_FOREST_ROADMAP.md` 想做 AI 头脑风暴。

结果是功能很多，但没有一条核心链路被做深。

### 1.2 已有、可以直接用于匹配的部分

- **用户侧**：`UserSkill` / `UserInterest`（名称 + 1–5 级），`Profile` 里有学校、专业、城市、语言、简历链接（`backend/models/userModel.go`）。
- **项目侧**：`Project` 有 `Topic`（jsonb）、`ProjectScenario`（course / research / product / personal）、学校、班级、周期（`backend/models/projectModel.go`）。
- **招募**：`ProjectPost.Spots`（需要的角色和名额），以及可见性设置（公开 / 本地 / 同校邮箱域）。
- **申请流程已经端到端跑通**：`ProjectApplication`、自定义问题 `ApplicationQuestion`、发起人审核（`ApplicationsList.tsx`）；邀请链接（`ShareLink`、`ProjectInvitation`）和私信也都有。
- **基础设施**：pgvector 和 Vertex embedding（`text-embedding-004`，768 维）已经在 RAG 里用上了（`ai-service/services/rag/`）。
- **AI 引导建项目**（onboarding）已经能问出项目目标、技能需求和时间线，但这些结果**没有保存成结构化数据**。

### 1.3 缺失或有问题的部分

- **没有任何"人 ↔ 项目"的打分、召回或推荐接口。**`PostSuggestion` 模型是空壳，它的主键还是 uuid，和其他表用的 uint 主键对不上。
- **项目浏览接口 `GetProjectPosts` 的筛选是坏的**：
  - 对 jsonb 字段用了 `projects.topic IN (?)`（`backend/controllers/projectController.go:162`）；
  - 查询了一个不存在的 `project_posts.available_spots` 列（第 170 行）；
  - 语言筛选被直接跳过。
- 前端 `Projects.tsx` 把写死的 mock 数据和真实 API 数据混在一起展示。
- `suggestionRouter` 在 `main.go` 里被注释掉了，前端 `suggestionApi.ts` 调用的是不存在的接口。
- crawler 用 mpnet 生成的向量和 ai-service 用 Vertex 生成的向量都是 768 维，但**不在同一个向量空间**，不能混在一起算相似度。

## 2. 匹配的核心功能：一条最小闭环

1. **结构化的项目需求**：用现有的 AI onboarding 对话产出"角色卡"，包括每个角色需要的技能和等级、每周投入时长、周期、项目阶段、是否线下。发起人不用自己写招募帖，AI 帮他把需求说清楚。
2. **结构化的用户画像**：从简历、GitHub 或一段自我介绍里，用 LLM 抽取技能（并做归一化）、兴趣、可投入时间、目标（学东西、做作品集、拿奖）。
3. **匹配引擎**：分三步。
   - 硬过滤：可见性、学校或地区、时间段；
   - pgvector 向量召回：角色向量和用户向量比对，取 top 50；
   - LLM 精排 top 10–20：给出分项得分和一句推荐理由。
4. **两个入口**：用户侧是"推荐给你的项目"，发起人侧是"推荐的候选人"，然后接上现有的一键申请、邀请和私信。
5. **反馈数据**：记录曝光、点击、申请、通过、拒绝，用来评估效果，后面也可以用来调权重。

**北极星指标**：组队 4 周后团队仍然活跃的比例，或第一个里程碑按时完成的比例。不用"申请通过率"作为北极星，因为通过之后有人摸鱼才是真正的失败。

## 3. 五个核心难点与对应方案

总原则：**不要指望 AI 从聊天里"猜准"一个人，而是让用户用行为和付出的成本来证明自己，再让 LLM 去整理这些证据。**

| 问题 | 严重程度 | MVP 阶段的处理 |
|---|---|---|
| 四、贡献难量化（口头感兴趣但不投入） | **最致命** | 必须做 |
| 五、信息冗余、分散注意力、缺少信任 | **很致命** | 必须做 |
| 一、AI 画像不准、metrics 难定义 | 中等 | 换个问题来解决，不硬磕 |
| 二、热门项目和冷门项目冷热不均 | 中等 | 用简单的排序规则处理 |
| 三、idea 被抄走 | 真实存在，但不能过度保护 | 轻量处理 |

组队失败最常见的原因是"有人不干活"和"互相不信任"，而不是"匹配不够精准"。

### 3.1 画像不准：不追求准确画像，改为"基于证据的画像"

- **只画和这个角色相关的那一部分**：不为每个人生成完整标签，只针对具体的角色卡问几个问题（例如"你用 React 做过什么"），按需逐步收集。
- **每条标签都附带证据**：区分"自述"和"有证据"两类（GitHub、作品集、站内完成过的项目），两者权重不同。
- **平台内的行为才是最真实的画像**：一个人按时完成了哪些任务是客观数据，所以**任务和里程碑系统要保留**，它是贡献数据的来源。
- **metrics 不衡量画像本身，只衡量结果**：推荐到申请的转化率、申请通过率、4 周存活率。

### 3.2 冷热不均：这是双边市场问题，靠排序规则调节

- **热门项目要限流**：名额满了就自动关闭申请或转为候补；排序时对待处理申请已经很多的项目降权，避免强者恒强。
- **冷门项目改为主动出击**：把匹配的候选人推给发起人，由发起人去邀请。现有的邀请功能可以直接用。
- **AI 帮冷门项目调整招募需求**：把大角色拆成门槛更低的小角色，或者降低每周投入要求。
- **冷门方向可以开订阅**：有合适的人注册时提醒发起人。

### 3.3 idea 保护：分层披露，不做重型保护

idea 本身不值钱，执行才值钱。保护过度会直接伤害"发现"这个核心价值。

- **分层披露**：公开层只展示问题、方向和需要的角色；核心思路和细节，只有发起人通过申请后才能看到，可以加一个轻量的"保密承诺"勾选。
- **留下时间戳记录**：项目创建和修改都有记录，发生争议时可以证明谁先提出。
- **用实名和信誉约束**：同校邮箱验证和举报机制都已经有了，被举报抄袭会影响信誉分。

### 3.4 贡献难量化：从"声称感兴趣"变成"有成本的承诺"

- **让申请有成本**：每人同时最多有 3 个进行中的申请，申请时必须填写每周能投入几小时、能持续多久。
- **设置试用期**：加入后先完成一个 1–2 周的小任务，由现有任务系统派发。结束后双方确认是否继续，不合适可以低成本退出。
- **用站内数据计算可靠度**：任务按时完成率、响应速度、项目结束后的互评，合成一个可靠度分，反过来进入匹配排序，形成正循环。
- **新用户冷启动**：没有记录的新用户标为"新人"，不惩罚，但排序权重低于有可靠记录的人。

### 3.5 信息冗余：LLM 匹配不等于给用户看更多

- **少而精**：每天只推荐 3–5 个，不做无限刷的信息流。
- **每条推荐都要可决策**：一句推荐理由，加一个主要风险（例如"技能匹配，但他每周只能投入 5 小时"）。
- **信任优先**：同等条件下，优先推荐同校、同班、好友的好友、以前合作过的人（`Contact` 和学校邮箱域的数据已有）。
- **分阶段建立信任**：浏览 → 轻互动（在帖子下提问）→ 试用期 → 正式加入。
- **发起人看到的是 LLM 整理好的结构化候选人卡片**，可以横向对比，不用去翻聊天记录。

## 4. 强需求还是伪需求

结论：**是强需求，但有前提**。只在"必须组队、有截止日期、做砸了有后果"、并且**需要找认识圈子以外的人**的场景里成立。泛泛的"找对我的 idea 感兴趣的人"大概率是伪需求。

| 场景 | 判断 | 原因 |
|---|---|---|
| 课程小组作业、毕设 | 不是匹配需求 | 班内或熟人圈就能组队，痛点是有人摸鱼，属于协作工具要解决的问题 |
| 比赛、黑客松 | 需求真实，但周期太短 | 组完队用户就走了，留存差 |
| 长周期跨专业竞赛 / 双创项目 | **强需求** | 需要跨院系找人，周期长，有奖项和保研加分作为后果 |
| 实验室招本科生 | **强需求** | 学生不知道去哪找，导师难以筛选 |
| 学生创业找合伙人 | 痛点深但量小 | 信任门槛最高，已有竞品 |
| "我有个 idea，看谁感兴趣" | **偏伪需求** | 没有截止日期也没有后果，表达兴趣的成本为零 |
| 兴趣社交、找学习搭子 | 弱需求 | 替代品多，频率低 |

### 4.1 写代码之前怎么验证

1. **用户访谈**：访谈 20 个上学期做过小组项目或参加过比赛的学生，问他们当时怎么找的队友、踩过什么坑、如果有这个工具会不会用。如果大多数人说"找熟人就行，没什么问题"，说明需求偏弱。
2. **人工撮合 MVP**：选一门课或一场比赛，用表单收集需求，人工加 LLM 撮合。看两个数：有多少人愿意认真填承诺时长，以及 4 周后团队还在不在。
3. **看组织方的意愿**：如果老师或比赛主办方愿意让整个班或整个赛道都用你的工具来组队，那就是强需求的信号。

| G7 | 结项互评和信誉积累 | 可靠度可以跨项目、跨场景带走 |

## 6. 筛选与结论

### 6.1 筛选标准

1. 痛点强度
2. **是否需要找圈外的人**：不需要的话，就用不着匹配
3. 合作周期：周期越长，留存越好
4. 是否有组织方可以整体接入：决定冷启动难度
5. 是否有付费方
6. 现有替代品有多强
7. LLM 能带来多少增益
8. 和现有代码的契合度

### 6.2 短名单打分

| 场景 | 痛点 | 需要圈外 | 周期 | 组织方 | 付费方 | 替代品弱 | LLM 增益 | 代码契合 | 结论 |
|---|---|---|---|---|---|---|---|---|---|
| **A1 本科进实验室** | 高 | 高 | 高 | 高（系、科研办公室） | 中 | 中 | 高（读懂论文和研究方向、匹配兴趣） | **高**（论文模块、申请流程） | ⭐ 值得做 |

### 6.4 建议的组合

**主场景，按市场二选一：**
- 美国：**A1 本科进实验室**，可以顺带延伸到 A2 跨学科合作和 A4 短期科研助手；
- 国内：**B1 双创跨专业组队**，加上 B2 找指导老师和学校端的过程管理。

国内本科生为了保研，也有很强的进实验室需求，所以 A1 在国内同样成立，可以作为 B1 之后在同一所学校里开的第二个场景。

**所有场景都要做的横向功能**
- G1 角色卡：这是 LLM 最能发挥价值的地方。
- G2 中途补位：痛点最强，又没有专门的解决方案，可能成为差异化卖点。
- G6 试用期和 G7 互评：直接解决"贡献难量化"的问题。

**值得单独验证的新方向：G3 短期技能帮手**
- 把"组队"拆成"一个小而明确的任务"，承诺成本低，投入难量化的问题自然就弱了。
- LLM 正好擅长把模糊需求拆成边界清楚的任务，也擅长做技能的语义匹配。
- 风险是它可能慢慢变成一个外包或零工平台，要想清楚报酬怎么算：是给钱，还是给作品集和信誉。

**后期的变现方向：F1 企业命题**
有了学生池和信誉数据之后，企业愿意为"找到靠谱的学生团队"付钱。这是最明确的付费方，但要等学生侧的密度起来之后才做得动。

## 7. 中美市场对比

### 7.1 中国：双创竞赛跨专业组队 + 学校端过程管理

**主场景**：大创（大学生创新创业训练计划）、中国国际大学生创新大赛（原互联网+）、挑战杯。
- 周期在几个月以上，评审重视团队的专业搭配，加上保研加分、综测加分，学生的投入动力很强。
- 典型痛点：计算机系的学生找不到商科或设计的队友，文科生有想法却找不到能做技术的人，指导老师也难找。
- 数学建模、电子设计这类比赛周期短、队伍固定三人，适合作为引流入口，不适合当主场景。

**谁会付钱：学校，但要抓住学校自己的需求**
- 学生要的是队友，学校创新创业学院和教务处要的是**过程管理**：项目报名、中期检查、结题材料、数据统计。
- 产品形态是"学生端负责组队匹配，学校端负责过程管理和数据看板"。已有的任务和里程碑系统可以改造成过程管理功能。
- 风险：学校采购流程慢，可能要走招投标。前期可以先免费试点一个学院，积累案例。

**竞品和替代品**：QQ 群、微信群、小红书组队帖、学校表白墙；赛氪这类竞赛信息平台已有组队功能，但多是发帖加浏览，没有承诺机制，也没有过程管理。

**落地门槛较高，现有技术栈基本要重做**
- **产品形态**：要做微信小程序，用微信登录，Web 端不是主战场。
- **基础设施**：AWS 和 Vertex AI 在国内不能直接用，需要迁到阿里云或腾讯云，模型换成通义、DeepSeek、智谱等国产大模型。
- **合规**：网站要做 ICP 备案；面向公众提供生成式 AI 服务需要按《生成式人工智能服务管理暂行办法》备案，或者直接使用已备案模型的 API；学生个人信息的处理要符合《个人信息保护法》。
- 粗略估计，基础设施和合规这部分要多花 1–2 个月。

### 7.2 美国：本科科研招募

**主场景：本科生进实验室**
- 学生端需求强：申请研究生、医学院，科研经历几乎是必需品，很多人不知道哪个实验室在招人，只能挨个发冷邮件。
- 导师和研究生端：每学期收到大量冷邮件，很难判断谁靠谱。
- 池子在校内，身份可以用 .edu 邮箱验证，信任度高；合作周期是一学期以上。
- 现有的论文模块可以复用，用来展示实验室的研究方向，并帮学生快速读懂实验室的论文。
- 一些学校有官方的科研项目列表（如 UC Berkeley 的 URAP），但多是静态列表，没有匹配、筛选和承诺机制。

**次场景**：学校创业中心组织的创业比赛和孵化项目（工程 + MBA 跨专业组队）。

**建议避开的方向**
- 课程分组：CATME 已经覆盖了问卷分组和同伴互评，而且这个场景本身不需要大范围找人。
- 创业合伙人匹配：YC Co-Founder Matching 已经占位，而且免费。
- 黑客松组队：Devpost 和 MLH 的生态已经覆盖了。

**落地门槛低**
- 现有技术栈（Web、AWS、Vertex/OpenAI）可以直接用，产品文案和例子本来就是英文的。
- 合规：如果对接学校的学生记录，要遵守 FERPA；只用学生自己填的资料的话，压力小很多。
- 获客渠道：学校 Discord 和 Slack、社团招新、科研办公室、研究生群体。
- 付费方：系里或创业中心预算不大，但小额工具采购往往比国内学校快；也可以对学生做免费增值。

### 7.3 对比

| | 中国 | 美国 |
|---|---|---|
| 主场景 | 双创竞赛跨专业组队 | 本科科研招募 |
| 用户的核心动力 | 保研、综测加分 | 申请研究生或医学院、简历 |
| 付费方 | 学校创新创业学院（要卖过程管理） | 系、创业中心，或学生免费增值 |
| 主要竞品 | QQ 群和微信群、小红书、赛氪 | 学校官方科研列表、冷邮件、CATME（课程场景） |
| 技术改造量 | **大**（小程序、国内云、国产模型、备案） | **小**（现有栈直接可用） |
| 冷启动方式 | 接入一个学院的报名季 | 接入一个系或一个科研项目 |

### 7.4 先做哪个

主要取决于**团队在哪边、能直接接触到哪边的学校**。
- 能直接对接美国某所学校的系或科研办公室：**先做美国的科研招募**。改造成本最低，现有代码复用最多，一个学期就能验证需求。
- 团队在国内、手里有高校资源：**做国内双创组队**。但要把 1–2 个月的基础设施迁移和备案算进计划，而且一开始就按双端产品来设计，否则找不到付费方。

不建议两边同时做：技术栈、合规要求和获客渠道几乎没有交集。

## 8. 切入太窄会不会匹配不起来

**匹配能不能做成，看的是池子的密度，而不是总人数。**窄切入不会让匹配变难，"大而稀"的池子才会。真正的风险是窄过了头，池子小到根本不需要匹配，一张列表就够用了。

### 8.1 为什么窄反而更容易匹配

- 全国铺开、每个学校各有 50 个人：一个计算机系的学生想找本校的设计师，可能一个都找不到。
- 集中在一所学校、3000 个人：同一个人想找设计师，能有几十个候选人。

双边平台基本都是这样起步的：Facebook 先做哈佛，Uber 一个城市一个城市地开。

### 8.2 窄要窄在"信任边界"上，不要窄在"场景"上

- **边界要窄**：一所学校，有统一的身份验证，彼此的信任度高。
- **场景在校内要宽**：同一个池子同时承接大创、各类比赛、科研招募和自发的项目。参加这些的往往是同一批积极的学生，他们的画像、可靠度和贡献记录可以在不同场景之间通用。

"双创组队"或"科研招募"是**对外宣传的切入点**，用来获取第一批用户，而不是池子的边界。

### 8.3 量级估算（数字为假设，需实地核实）

以一所两三万人的综合性大学为例：
- 假设每年有 300 个项目在招人，每个项目缺 2 个角色，一共 600 个岗位；
- 假设其中 10% 的学生在某个时间段内想加入项目，也就是 2000–3000 人；
- 按专业打散后，每个岗位大约还有 10–30 个潜在候选人。

经验上每个岗位要有 5 个以上的合格候选人，匹配才有意义；少于 3 个的话，直接展示列表就够了。

**真正可能失败的不是人数不够，而是时间上对不上。**组队需求集中在报名季，供需双方不在同一时间段活跃，人再多也匹配不起来。

### 8.4 小池子里，AI 的作用要换一个方向

大池子里 AI 主要做"筛选"；小池子里 AI 应该做"激活"和"扩展"：
- **语义扩展**：会 Flutter 的人也能做 React Native，统计专业的学生也能做数据分析。
- **把被动候选人推给发起人**：很多人有资料、但没有主动申请，系统直接推荐给发起人去邀请。
- **调整岗位需求**：没有人申请时，AI 建议降低门槛或拆分角色。
- **在时间上集中供需**：报名季前办"组队周"，人为制造时间上的密度。

### 8.5 流动性指标

- **岗位侧**：多少比例的岗位在 7 天内收到了 3 个以上合格的申请或邀请；
- **个人侧**：多少比例的求组队用户在 2 周内至少被接受一次。

两个数都高，说明密度足够，可以复制到下一所学校；偏低就先在校内扩展场景，再考虑扩大边界。

### 8.6 覆盖面怎么扩

1. **单校、多场景**：先把一所学校做密。
2. **同城或同区域多校**：允许跨校组队的比赛和项目先打通；在美国可以从同一个大学系统内部开始。
3. **复制到更多学校**：每所学校都是一个独立的密集单元，跑通的方法可以直接照搬。

起步窄不等于市场小。

## 9. 其他需要注意的问题

1. **频率低，留存难。**组队一学期只发生一两次。必须让组队之后的协作留在平台上（任务、里程碑、贡献记录）。协作功能不能砍，只是不要往 Jira 的方向做重。
2. **"跳单"风险。**匹配成功后团队很可能转去微信或 Discord，平台拿不到贡献数据，信誉体系失效。要给用户留在平台的理由：试用任务在站内派发；贡献记录可以导出成证明，能写进简历、拿给老师看。
3. **供需不对称。**通常是出 idea 的人多，会写代码、会设计的执行者少。产品要优先讨好稀缺的那一方。
4. **冷启动按组织来做，不要按个人。**一次接入一个班或一个比赛，池子里一下就有几十上百人。这同时回答了"谁付钱"的问题。
5. **信誉系统本身会被滥用。**要防报复性差评、互刷好评，允许申诉。评价最好是项目结束后双向匿名、汇总展示。
6. **合规和安全。**国内要符合《个人信息保护法》，美国涉及学校数据要注意 FERPA。陌生人线下见面要有安全提示。团队里的知识产权归属最好在加入时就约定清楚。
7. **先确定市场。**两边的渠道、合规要求、竞品和 LLM 选型完全不同。
8. **避免继续堆 AI 功能。**每加一个功能，先问一句：它能不能提高"组队 4 周后的存活率"。

- AI onboarding（改造成生成角色卡）；
- RAG 和 embedding 基础设施。

粗略估算，冻结之后需要维护的代码会降到现在的 1/3 左右。
